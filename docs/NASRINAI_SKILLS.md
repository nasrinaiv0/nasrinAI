## Skill registry fields

Each skill in the JSON knowledge base has:

- `skill_id`: stable identifier suitable for retrieval and analytics.
- `group_id` / `group`: category identifier and display name.
- `name`: concise skill name.
- `description`: user-readable description.
- `status`: implementation status; `needs_verification` is the default until audited.
- `availability_note`: reminder not to overstate implementation.

## Recommended status lifecycle

| Status | Definition | Evidence expected |
|---|---|---|
| `implemented_verified` | Working and verified | Code path, integration/configuration and relevant passing tests |
| `partially_implemented` | Some functionality exists | Known working subset and documented gaps |
| `planned` | Design only | Product requirements or backlog item |
| `blocked` | Cannot proceed yet | Explicit dependency, permission, credential or infrastructure blocker |
| `needs_verification` | Unknown | Audit required |

## User-question handling

1. Detect whether the user asks for an overview, a specific skill, a comparison, or current implementation status.
2. Search the knowledge base by skill name, group, alias and task wording.
3. Return a concise answer and useful examples.
4. For live availability questions, check current configuration or verified implementation evidence.
5. If status is unknown, say so clearly rather than guessing.
6. Do not claim to have executed a workflow, edited a repository, created a file, or completed an external action unless the relevant tool confirms it.
7. Include sources when answering research questions and cite current documentation when making claims about live product behavior.

## Professional and safety boundaries

- **Legal:** general information, research and document assistance; not a lawyer or a substitute for qualified legal counsel.
- **Healthcare:** general health information and document explanation; not a doctor or a substitute for clinical assessment.
- **Finance:** informational analysis; no guaranteed outcomes or false claims of professional credentials.
- **Cybersecurity:** test only systems for which authorization exists.
- **External actions:** act only through available, authorized tools; confirm success from tool results.

## Architecture principles

- Select skills based on user intent and task requirements.
- Do not invoke all models simultaneously by default.
- Choose models based on capability, complexity, tier eligibility, tool requirements, latency, context size, cost and configured provider policy.
- Keep specialist skills as orchestration/configuration, not as a requirement to create a separate foundation model for every profession.
- Separate a skill being described in this catalog from a skill being enabled and verified in production.
